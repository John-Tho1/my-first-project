### livep2-concurrency
- Q: Q1. Is the lock order sound, and does setLivePublishPaused taking the daily lock first mean every send decision that starts after a committed pause always sees the pause?
  - A: The lock order is sound. Only two places take cs_live_publish_daily: beginSend (account share → item → job → cs_rate → cs_live_publish:<ref> → daily → live_publish_controls FOR SHARE) and setLivePublishPaused (daily → controls FOR UPDATE → plain audit insert). recordAudit takes no locks, and nothing that holds the daily lock waits on a row lock that beginSend holds, so no cycle is possible. On real Postgres under READ COMMITTED (the default): the pause commits before its advisory lock is released (locks are released after ProcArrayEndTransaction). beginSend's next statement after pg_advisory_xact_lock takes a fresh snapshot, so it sees the pause and the competing worker's intent. On the only shipped driver (PGlite 0.5.8), every query and transaction is serialized by PGlite's transaction mutex (query() wraps _runExclusiveTransaction), so the advisory locks never contend and the PGlite rac…
- Q: Q2. Is 'counted only while inside the window' (a retry more than 24h later counts as new) the right reading of D39's 'retries and continuations are not counted again'?
  - A: Yes, and it is safe. A job is exempt while any of its live intents is inside the window, and each retry moves its lastAt forward, so an exempt job keeps holding its slot. Distinct jobs with an intent in the window are therefore never more than max, and each job publishes at most once (no re-post after a publish_attempt). The exemption cannot exceed the cap. Counting a retry after more than 24h as new matches 'posts in the last 24h': the earlier intent either never posted, or the job would not be retrying. Boundary checked: created_at > now−24h, with availableAt = lastAt+24h freeing the slot exactly at availableAt, which is consistent and tested. The `now` used is clock() captured before the PGlite mutex wait, which only makes the check more conservative.
- Q: Q3. If a continuation after an ambiguous outcome is stopped by the pause, should it go to a waiting state instead of BLOCKED so it does not get stuck behind outcome_unknown?
  - A: It should not be a dead end, but RETRY_WAIT/auto-wait is the wrong fix: it would send automatically after resume, contradicting the resume route ('보류된 작업을 자동으로 다시 보내지 않는다'). Keep BLOCKED, and let retryItem accept a BLOCKED job whose block is a pre-intent not_sent:true block (paused, daily limit or credential) that came directly after a reconcile 'resume', since reconcile has already proven the remote step unpublished. Details are in the P2 finding at jobs.ts:1543. Today the item cannot be retried or reconciled, because BLOCKED is not reconcilable.
- Q: Q4. Is it acceptable to exclude live_publish_controls from export so a restore starts as 'not paused'?
  - A: Acceptable. Same-environment add_missing restore never touches the row, because the table is neither exported nor deleted. On a new environment, publishing still needs PUBLISH_MODE/APPROVAL_REF/MAX_POSTS env values, which default to disabled, and restored in-flight jobs are restoredNeedsReview and never re-sent. It is also correctly in RETENTION_PROTECTED_TABLES. The FK uses ON DELETE RESTRICT on users; restore never deletes users, so there is no conflict.
- Q: Q5. Should executePlan reject (or warn) while paused or at the daily limit, or is queueing and blocking at send time correct?
  - A: Send-time checks must stay the authoritative ones: the cap is time-dependent, and scheduled items run later. An execute-time pre-check would only be advisory. A non-blocking warning, or a reject while paused, is a UX choice and not required for safety. Rejecting at execute for the daily cap would be wrong for scheduled posts whose window may have freed by the scheduled time.
- Q: Q6. Is the conservative choice of no upper bound on the window, so that future-dated intents are counted, acceptable?
  - A: Acceptable: it fails closed. One side effect worth documenting: a large forward clock jump followed by a correction leaves those intents counted until the clock catches up plus 24h, and available_at will show that far-future time. The operator remedy is to raise PUBLISH_LIVE_DAILY_MAX or remove it. This does not create an over-limit path.

- Q: Q1. Is the lock order sound, and because setLivePublishPaused takes the daily lock first, does any send judgement that starts after a pause commits always see the pause?

- Q: Q2. Is 'already counted only while in the window' (a retry after 24h counts as new) the right reading of D39's 'retries and continuations are not counted again'?
  - A: Yes, and it is the safe reading. The cap is about live posts per rolling 24h. A job whose earlier intent has left the window is no longer counted anywhere. The adapter never re-publishes after a marker, so a retry can only publish a post that has not been published yet, and that post lands in the new window. Counting it there keeps 'at most N distinct jobs with live intents in any 24h window'. Inside the window the exemption cannot add an extra post, because one job is one post.
- Q: Q3. If a continuation after an ambiguous outcome is blocked by the pause, should it go to a waiting state instead of BLOCKED so it is not stuck behind outcome_unknown?
  - A: It should not stay as it is: today it is a dead end with misleading text (finding 3). It fails closed, though, so it is P2. I would not use an auto-retrying wait state for the pause, because D39 and the UI promise that resuming does not send by itself. Better: when reconcile returns 'resumable' (steps prove no publish_attempt and no publish), mark the current intent as not published, as the definitive not_found branch already does with fillIntent 'rejected', so the normal 재시도 works after resume or after the window frees. Or let retryItem accept outcome_unknown when the event before BLOCKED was 'resume' and lastErrorCode is live_publish_paused or live_publish_daily_limit. The same dead end exists for a daily-limit block after the 24h window and for credential_blocked.
- Q: Q4. Is it acceptable to exclude live_publish_controls from export and start 'not paused' after restore?
  - A: Yes, from a safety standpoint. Restore only adds rows (add_missing / empty_only) and never deletes, so restoring into the same environment keeps an existing pause row. In a new environment the restore cannot cause a live send by itself: jobs come back read-only (restoredJobState plus restored_needs_review, and retryItem refuses), linked live accounts become needs_reconnect (credentials are excluded), and stale approvals are revoked. Any new live send needs a fresh explicit execution and is judged against that environment's own switch. The table is in RETENTION_PROTECTED_TABLES and in EXCLUDED_TABLES, and the parser rejects unknown tables. Optional nicety: the restore report could mention that the pause switch is not carried over.
- Q: Q5. Should executePlan refuse (or warn) while paused or at the daily cap, or is queueing and blocking at send time correct?
  - A: Queueing and blocking at send time is correct as the authoritative check (fail closed, under the locks). A refusal or warning in executePlan would only be a convenience. If added, it must stay advisory, sit alongside the beginSend check without replacing it, and not count queued jobs as used, because the cap counts intents.
- Q: Q6. Is it acceptable that the window has no upper bound, so future-dated intents (clock skew) are counted?
  - A: Yes. It can only over-count, which is the fail-closed direction. The only side effect is that available_at can land more than 24h ahead and the cap can block early while the clock is behind. That is acceptable, and a one-line note in the README is enough.

### expiry1-script
- Q: Q3: Is the failure window between the key mv and the cert mv risky enough to justify an atomic directory swap?
  - A: No. Both are same-directory renames, atomic per file on POSIX and in MSYS/Cygwin, microseconds apart. A failure there needs a rename error such as a Windows AV or file lock. An atomic directory swap is also impractical here, because the same folder holds backup-*/ and other pems, and Windows cannot atomically swap directories. The cheap fix is what matters, because current handling makes the window worse than it needs to be: on a cert-mv failure the EXIT trap deletes $tmp_cert, the only cert matching the new key, and leaves new key + old cert. Roll the key back from $backup/$KEY_NAME automatically and keep or print tmp_cert (see the dev-cert.sh:185 finding). Keeping key-first order is fine.
- Q: Q5: Should check exit 0 for an expired cert, or return non-zero so scripts can detect it?
  - A: Exit 0 is consistent with the spec and the script header: the plan only requires that check prints notAfter and days left, and the header defines 0 as success, 1 as execution failure and 2 as usage error. It is not a defect. If machine detection is wanted, add a distinct code such as 3 for expired (and optionally 4 for within 14 days) rather than reusing 1, which already means missing openssl or file or a read failure. Document it in the header and README, and add a test using the existing STUB_ENDDATE stub.
