### F1 — [P1] OIDC issuer가 달라져도 기존 세션이 무효화되지 않는 경계

- 위치: `Content_Studio_Execution_Pack/packages/domain/src/oidc.ts:140` (`normalizeIssuer`), 사용 위치 `:162`; 통과 지점 `apps/web/lib/session.ts:44`.
- 문제: `new URL(raw.trim()).href.replace(/\/$/, '')`가 발급자 경로의 마지막 `/`를 제거한다. 따라서 `https://idp.example/tenant`와 `https://idp.example/tenant/`가 같은 세션 정책 지문을 만든다. D40-3은 issuer 변경 시 기존 세션 거부를 요구한다.
- 영향: 운영자가 발급자 식별자를 위와 같이 변경해도, 이전 발급자에서 만들어진 만료 전 세션이 계속 owner 인증을 통과한다. 기존 유효 세션과 설정 변경이 필요한 경계이며, 새 임의 사용자가 곧바로 로그인할 수 있다는 주장은 아니다.
- 프로토콜 근거: OIDC의 issuer 식별은 메타데이터 및 ID token의 iss와 정확히 일치해야 한다. 서로 다른 issuer를 경로 끝 슬래시 삭제로 합치는 것이 안전하다고 볼 수 없다. [OpenID Connect Discovery §4.3·§5](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderConfigurationValidation).
- 재현(실행 완료): 합성 메모리 PGlite에 owner와 이전 issuer 지문을 가진 유효 세션을 생성 → `validateSessionToken`을 이전/변경 issuer로 각각 호출 → 둘 다 통과. 대조군으로 다른 호스트 issuer를 주면 거부.
- 실제 출력:
  ```json
  {"beforeIssuer":"https://idp.example/tenant","afterIssuer":"https://idp.example/tenant/","sameFingerprint":true,"oldSessionAcceptedAfterIssuerChange":true,"differentHostRejected":true}
  ```
- 재현 명령(앱 루트에서):
  ```sh
  node --import tsx /workspace/cs-review-evidence/issuer-repro.mts
  ```
- 증거: `issuer-repro.mts`, `issuer-repro.log`. 실제 IdP 호출 없이 제품의 migration·세션 저장·세션 검증 코드를 실행했다. 재현 스크립트 exit 0은 **결함 재현 성공**이지 제품 PASS가 아니다.
- 기존 테스트가 놓친 이유: `tests/integration/fullrev2-session-policy.test.ts:140–148`은 issuer 끝 `/` 변경 뒤에도 인증 통과를 기대한다. unit `packages/domain/src/oidc.test.ts:204`도 같은 전제를 고정한다.
- 제안: 세션 정책의 issuer는 실제 OIDC issuer 식별과 일치하는 기준으로 보존·비교하고, 경로 `/tenant` → `/tenant/` 변경 시 옛 세션을 거부하는 회귀 검사를 추가한다. 제품 코드나 테스트는 이번 검증에서 고치지 않았다.

실행 환경 Linux, Node `v24.19.0`, Vitest `5.0.1`, Chromium `151.0.7922.173`. 실제 모델 세부명/추론 강도는 런타임 화면으로 확인하지 못해 대기열 주석의 gpt-6-astra/xhigh라고 주장하지 않는다.

기본 pnpm은 11.19.0이었다. 최초 install은 기본 사용자 캐시 경로 mkdir ENOENT로 실패했고, `/tmp` XDG/cache/store 지정 후 성공했다. unit은 이때 실행했다. 이어 문서 고정 버전 pnpm 12.6.0을 임시 npm 캐시에 설치해 frozen install을 다시 성공시켰고, 나머지 pnpm 명령은 해당 버전으로 실행했다. lockfile 및 추적 파일은 그대로다.

### 브라우저 검증의 정확한 범위

- 별도 `/tmp/cs-browser-*` 합성 DB/파일, localhost:3100, AUTH_MODE=dev, LLM/STT/OAuth mock, 게시·수집 disabled.
- 브라우저 외부 호스트 요청은 route에서 차단. 실제 API·계정·비밀 사용 없음.
- FormData 로그인 200, 실제 폼 POST의 충돌 409 후 서버가 제공한 재저장 폼 제출 성공(`saved_version=3`, Origin `http://localhost:3100`), 같은 본문 JSON 저장 `200 unchanged:true` 확인.
- `error=__proto__&upload=constructor&account_error=toString&live_error=hasOwnProperty` 조합으로 `/`, `/contents`, 합성 원고 상세, `/brand`, `/settings`, `/ops`, `/collect`, `/imports`, `/ideas` 9개 페이지 HTTP 200, pageerror 0.
- `/distribute/new`는 필요한 파생본 없이 접근해 404였다. 스크립트의 'PASS … 404'는 500 없음만 뜻한다. **이 페이지의 정상 폼 렌더 검증으로 계산하지 않았다.**
- 수집 실행 상세·가져오기 상세·복원 상세·배포 상세 등 모든 17개 화면을 실제 브라우저로 검증한 것은 아니다. 관련 unit/integration 렌더 검사는 별도다.

## 미실행·한계·차단 사항

- 실제 PostgreSQL 다중 연결, advisory/FOR SHARE 경합: 미실행. 현재 앱의 DB_DRIVER=postgres 구현이 없다(`packages/db/src/client.ts`); PGlite 단일 연결 시험은 이를 대체하지 못한다.
- 실계정 Threads/OIDC/LLM, 실제 게시·원격 철회·유료 호출: 사용자 요청 범위 밖이라 미실행.
- Windows Git Bash·macOS·Safari·Firefox, 사용자 PC HTTPS 실행기: 미실행.
- 실제 디스크 부족/전원 차단/SIGKILL/systemd 데이터 볼륨 분리: 미실행. 셸 fixture·I/O 주입 결과와 구분한다.
- 기존 15~20 커밋 각각의 역사적 테스트 전체, mutation test: 이번에는 미실행. 구현자의 mutation PASS를 우리 결과로 쓰지 않았다.
- 전체 앱에 대한 무결함 증명이나 배포 승인 아님. F1 외 확정 추가 지적 없음은 이번 지정 범위에 한정한다.
- 자동 승인 심사에 의한 작업 거부 없음. 캐시 경로 문제는 임시 writable 경로로 해결했다. 최종 승인 요청이나 외부 작업 대기는 없다.
