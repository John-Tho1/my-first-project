## Deviations / choices needing confirmation
1. **Revoke invalidates approvals** for that account (`invalidated:account_changed`, approved variant → review), in the same transaction. Reconnect and refresh do **not** invalidate, because the callback refuses any identity change (409 mismatch) and `provider_account_id` in the snapshot is unchanged. Expiry blocks execution but does not invalidate. This is the conservative reading of D17 ("계정 상태 변경 → account_changed"). Confirm.
2. After revoke, `credential_state` stays `linked`, so a mock account that was once linked stays **blocked** until reconnected. It does not fall back to plain mock behaviour. Confirm, or add a "연결 정보 없이 모의로 되돌리기" action.
3. Added the column `channel_accounts.credential_state`, which is exported in bundles but ignored by restore's equality check. Without it, "restored accounts show 다시 연결 필요" could only hold for live accounts.
4. Route paths use the existing `/api/channel-accounts/{id}/…` prefix instead of `/api/accounts/{id}/…` (the brief said "e.g.").
5. The mock consent step is an in-app GET route (`/api/oauth/mock-threads/authorize`). It requires login and auto-consents, with no consent page UI. Test-only query params (`mock_user`, `mock_grant`, `mock_deny`) are accepted in all builds because the endpoint only ever issues mock tokens. Gate them by `NODE_ENV` like D19-c?
6. Mock provider state is process memory. After a dev-server restart, stored mock tokens become `invalid_token` on check/refresh (status → error → reconnect). Execution does not call the provider, so the mock publish path is unaffected.
7. `liveOAuthReadiness` also lists `SECRETS_MASTER_KEY` and `PUBLISH_MODE=enabled` as live preconditions.
8. A scope-short grant (`mock_grant`) is **stored** and shown as `needs_reconnect / scope_missing`, which blocks execution. The alternative is to reject at callback.
9. A provider `error` at callback still consumes the state (single-use regardless of outcome). A state with a mismatched session is also consumed (fail-closed). This means an attacker holding the victim's state URL can burn it, but cannot use it.

## Remaining risks
- Concurrency: `oauth_credentials` is not part of the global lock order. Reconnect/revoke lock the account FOR UPDATE; the execution gate reads credentials without a lock inside the execute/beginSend transaction. A revoke racing with `beginSend` could let one MOCK send through. Real PostgreSQL behaviour has not been verified.
- `refreshCredential`/`checkCredential` call the provider outside a transaction. Refresh uses an optimistic compare on the old ciphertext. Check updates without compare, so a check's status could overwrite a concurrent reconnect's fresh `active`. Low impact; it self-corrects on the next check.
- `oauth_states` cleanup happens only when the same owner starts a new connect. Abandoned states stay until then; they are hashed/sealed and expire.
- The `credential_unreadable` extra `problem` reveals the failure class (auth_failed/unknown_key_version). No secret, but it is information.
- Scope names and the 60-day / 7-day thresholds are provisional until T14 confirms them with official docs.
- The UI (server components) was not rendered in tests. Redaction for HTML relies on the view object (`accountHealthView`) having no token fields.

## Core design: token generation + per-account lock order
- **Token generation.** `token_generation` goes up by 1 each time a new token is stored: callback exchange, reconnect or refresh. Re-encrypting for key rotation does **not** change it.
- **One lock order.** Every credential mutation locks the `channel_accounts` row FOR UPDATE, then the `oauth_credentials` row FOR UPDATE (`lockAccountCredential`, packages/db/src/oauth.ts). This covers:
  - callback store
  - refresh (read and write-back)
  - check (read and write-back)
  - revoke (mark and finalize)
  - rotation (per row)
  - decrypt-failure recording (done inside the read lock in `readForUse`)
- **Write-back rule.** Provider calls always run outside transactions. Every write-back compares the generation it read (`sameLiveGeneration`: same generation, not revoked, not revoking, ciphertext present).
- **Execution side.** `beginSend` and `retryItem` now take the item's account FOR SHARE **before** the item lock (`shareLockItemAccount` in jobs.ts; `executePlan` already did this). If a blocked state (`revoking`, revoked, expired) commits first, the send transaction reads it after acquiring the lock and creates no send intent.

## Questions for Codex
1. `beginSend` and `retryItem` read the immutable `channel_account_id` unlocked, then share-lock the account before the item. Is that consistent with the global lock order, and free of new deadlock paths against `setChannelAccountState` and revoke (both take account FOR UPDATE, then items)?
2. When a refresh write-back is discarded, we revoke the newly issued token at the provider. Is that the right rule, or should we store it when the only change was a concurrent refresh? Without the generation we cannot tell which of two valid tokens is newer, so we keep the committed one.
3. On `incomplete`, revoke keeps the row `revoking` with its ciphertext. Is that acceptable, or should the same call also revoke the newer generation?

## Core design: pending reconcile record
- **Blocking does not depend on `status`.** `credentialHealth` (domain) checks `pendingKind` before revoked/error. A pending record gives `error` with reason `pending_<kind>` and `usable=false`. So the same gate in `executePlan`, `beginSend` and `retryItem` blocks it with no code change there. The view adds `pending_reconcile` (kind only; no op id or ciphertext).
- **`markAfterIssuance`** (one tx, account → credential lock) writes after-issuance failures:
  - `markStoreFailed` → `status='error'`, `refresh_store_failed`, only when `sameLiveGeneration(cred, G)`.
  - `pending` → T2 sealed with the current key (AAD purpose `oauth_pending_token`).
    - Kind is `refresh_unknown` only if the row is live and generation ≤ G+1 (our commit may have happened). Otherwise it is `cleanup_revoke`, since T2 cannot be the current token.
    - If there is no row (first connect), it inserts a **placeholder**: `revoked`, no ciphertext, `revocation_epoch 0`. A real disconnect always bumps the epoch to ≥ 1, so "revoked + epoch 0" is unambiguous. The placeholder is deleted when the record clears; the epoch stays 0 either way, so state-epoch checks are unaffected.
    - If another pending record already exists → `occupied` (not overwritten; the existing record keeps the account blocked).
  - Seal or write failure → audit `oauth.pending_record_failed` (`refresh_pending_record_failed`). A second small tx then sets a live row to `error`/`refresh_pending_record_failed`.
- **`revokeAtProvider`**: `token_revoked` and `invalid_token` → `ok_already_revoked`. `provider_error` → `unknown`. Other errors → `failed`. Failed and unknown are audited as `oauth.cleanup_revoke_failed` / `oauth.cleanup_revoke_unknown` with a `context`.
- **Who reconciles**: `checkCredential` (returns the reconciled health), `refreshCredential` (409 `pending_reconcile` while still pending), and `refreshExpiringCredentials` (the worker tick). The tick handles all pending rows first, including revoked and placeholder rows, and returns `pendingResolved`/`pendingRemaining`. Expiry refresh skips rows that have a pending record.

### Decision table (`reconcilePendingCredential`, also in code)
Under the lock it reads op id, P (pending) and C (stored). Provider calls happen outside the tx. The write-back happens only if the op id is unchanged. A `revoking` row is left to the disconnect. A revoked or placeholder row is always treated as `cleanup_revoke`.

| Kind | Condition | Provider | Result |
|---|---|---|---|
| any | P unreadable (no key, wrong key) | none | stays pending (blocked) |
| refresh_unknown | C unreadable | none | stays pending: cannot compare |
| refresh_unknown | C == P (it was stored) | accountInfo(C) | keep, no revoke, clear; C valid → `active`, invalid → `error` (provider code) |
| refresh_unknown | C ≠ P | revoke P + accountInfo(C) | revoke ok → clear; C valid → `active`, invalid → `error refresh_store_failed` (P cannot be proven stored, so it is revoked and the user reconnects). Revoke failed or unknown → kind becomes `cleanup_revoke` and stays (C status recorded the same way). |
| cleanup_revoke | — | revoke P | ok → clear (status unchanged; placeholder deleted); failed or unknown → stays |

Status writes require `sameLiveGeneration(cred, generation read)`, so a newer reconnect is never touched. A transient C check (`provider_error`) leaves the status alone.

## Core design change: pending records move to their own table
FIX3 kept one pending slot per account in `oauth_credentials.pending_*`. FIX4 moves it to **`oauth_pending_tokens`**, one row per obligation:
- Columns: `id`, owner + account (same-owner FK to `channel_accounts`), `kind ∈ {refresh_unknown, cleanup_revoke, verify_current}`, `sealed_token`/`key_version` (sealed P, AAD purpose `oauth_pending_token` as before; empty only for `verify_current`), `base_generation`, `on_invalid_code`, `source`, `revision`, `attempts`, `next_attempt_at`, `last_result`, timestamps.
- CHECKs: kind list; `verify_current ⇔ no seal`; seal and key version together, seal starts with `csk1:`; `verify_current` needs `base_generation`; counters non-negative. Indexes on (owner, account) and `next_attempt_at`.
- Excluded from export/restore (`EXCLUDED_TABLES`), retention-protected (`RETENTION_PROTECTED_TABLES`), resealed by `secrets:rotate` (counted as `pendingTokens`, report line `정리 대기 봉인` unchanged).
- **Health**: `credentialHealth` gets a top-level `pendingKind`, checked **before** "no credential". So an account with pending rows is blocked even with no `oauth_credentials` row (first connect). With several rows, the shown kind is the first of `refresh_unknown → verify_current → cleanup_revoke`. The view adds `pending_count` (no ids, no seals).
- **No placeholder rows.** First-connect failures write only a pending row. No code path deletes `oauth_credentials` rows any more.
- All pending writes take the account → credential lock first. Execution takes the account lock FOR SHARE, so it reads after a committed pending write.

### Migration 0033 data step
1. Copy each 0030 pending record into `oauth_pending_tokens`, keeping the id (= old `pending_op_id`), kind, seal and key version. AAD is unchanged, so nothing is resealed. `source='migrated_0030'`, `base_generation = token_generation` for `refresh_unknown`.
2. Delete only **0030 first-connect placeholder rows**. Every condition must hold: pending present, `revoked`, `revocation_epoch 0`, no ciphertext, no `revoke_op_id`, generation 1, empty scopes, **and the account's `credential_state='none'`**. A real stored credential always sets `linked`, and disconnect keeps `linked`. So a legacy (pre-0029) `revoked + epoch 0` row is `linked` and is never deleted. The pending row still blocks the account after the delete.
3. Drop the 0030 columns and their 3 CHECKs.

### Reconcile (`reconcilePendingCredential`) — per account, all rows
- **Read** (under lock): every pending row (revision, kind, opened P), the credential identity (`id|generation|revocation_epoch|status|revoked|has token`), and C.
- **Provider** (outside the tx): revoke each P that needs it. Check C at most once.
- **Write** (under lock): apply only if the credential identity **and** every read row's revision and kind are unchanged. Otherwise write nothing and **re-run against current state** (up to 3 passes, then `still_pending`). Row updates and deletes also filter on the read revision.

| Kind | Condition | Provider | Result |
|---|---|---|---|
| any | key missing / P or C unreadable / provider unavailable / `revoking` | none | row kept; `attempts+1`, `next_attempt_at` pushed back, `last_result` = problem |
| refresh_unknown | C == P | check C | valid → delete, `active` · invalid → delete, `error`(provider code) · **unknown → becomes `verify_current`** (seal dropped, `base_generation`=C's generation) |
| refresh_unknown | C ≠ P | revoke P + check C | P ok: valid → delete/`active`, invalid → delete/`error refresh_store_failed`, **unknown → `verify_current`** (`on_invalid_code=refresh_store_failed`) |
| | | | P failed/unknown: row → `cleanup_revoke`; C status written if decided; **if C unknown, a separate `verify_current` row is inserted** |
| cleanup_revoke | — (also refresh_unknown on a non-live row) | revoke P | ok → delete · failed/unknown → kept |
| verify_current | live and generation == `base_generation` | check C | decided → delete + status (`on_invalid_code` ?? provider code) · unknown → kept |
| verify_current | generation changed / not live | none | delete. The new generation came from a callback, which checks the account; a revoked row is blocked anyway. |

Status writes still need `sameLiveGeneration(cred, generation read)`. A transient C check never changes status and never clears the block.

### Disconnect (`revokeCredential`)
Phase 1 reads all pending rows (id, revision, opened P). Phase 2 revokes each P, then C. Phase 3 changes only the rows it read, and only at the same revision:
- confirmed revoked → delete;
- failed or unknown → `cleanup_revoke` with revision +1;
- `verify_current` → deleted only when this disconnect actually revoked the credential.

Unreadable rows are left for reconcile. The audit `oauth.revoked` gains `pending_tokens` and `pending_tokens_revoked`. There is one `cleanup_revoke_failed`/`_unknown` audit per failed row.

### Worker sweep (`refreshExpiringCredentials`)
It selects accounts that have rows with `next_attempt_at ≤ now`, grouped by account and ordered by the earliest due time, then account id, up to `limit`. Every attempt pushes `next_attempt_at` back by 1 min × 2^(attempts−1), capped at 1 h. This includes stuck/undecryptable rows. If reconcile itself throws, a locked fallback update still pushes the time back. User `check`/`refresh` ignore the backoff and always try. Expiry refresh skips accounts with any pending row (`NOT EXISTS`).

## Remaining risks
- **Seal or write failure at record time** still loses the token record. It is audited (`oauth.pending_record_failed`), and a live row is set to `error refresh_pending_record_failed`. On first connect there is no row to block, so that token is unrecorded. This needs a key misconfiguration or a DB failure right after issuance.
- **`checkCredential` without pending rows** still maps a transient provider error to `status: active` (pre-existing FIX1 behavior, unchanged here). The `verify_current` path does not go through it.
- **Re-run limit**: under constant concurrent change, reconcile gives up after 3 passes with `still_pending` (blocked; the next check or tick retries). Each pass may repeat provider revokes, which are idempotent in the mock (`token_revoked`/`invalid_token` → already revoked).
- **Backoff numbers** (1 min doubling to 1 h) are provisional. The user `check` ignores them.
- **`invalid_token` at revoke = already revoked** (FIX3 rule, unchanged). It must be confirmed against the real provider (T14 note).
- Concurrency is hook-injected on PGlite's single connection, not true parallel PostgreSQL.

1. Is per-row `revision` + credential identity (`id|generation|epoch|status|revoked|has token`) enough to make the write-back safe? Rotation reseals without bumping revision because the token is the same. Is there a path where that lets a stale decision through?

## Remaining risks
- **Still a lease, not a lock** (Codex FIX7 Q2): a provider call longer than the lease lets one more resumer call the provider for the same op. Provider revoke is treated as idempotent (`invalid_token` = already revoked) — must be confirmed against the real provider.
- A user disconnect always joins immediately, even while a worker holds the lease (intended: explicit user action). That can still produce one extra provider call per user click during an in-flight worker resume.
- The due check compares DB timestamps with the worker's `now`; a worker with a clock far behind the DB writer only skips more (never resumes early) because the lease equality check is clock-independent.
- Concurrency remains hook-injected on PGlite's single connection.
